# ADR-003: SQLite 备份采用进程内定时快照 + 轮转保留

## Status: Accepted (2026-08-30)

## Background

数据文件 `./data/data.db` 仅有一份，依赖 Docker 卷持久化。卷能防"容器销毁"，防不了：误操作覆盖（`store.write` 是全量替换语义）、进程在写盘过程中崩溃导致文件损坏、卷所在磁盘故障。需要定期备份 + 轮转保留。

sql.js 的关键特性：数据库整个驻留内存，`db.export()` 一次性导出完整数据库 Buffer，`persistDb()` 用 `fs.writeFileSync` 全量覆写 `data.db`。这意味着：
1. 任何时刻调用 `db.export()` 都能得到一个**逻辑一致的完整快照**（单线程事件循环内无并发导出），备份不需要 SQLite 的在线备份 API
2. 但 `fs.writeFileSync` 非原子：写盘中途崩溃会留下**截断/损坏**的 data.db。这是现有代码的数据丢失隐患，与备份目标直接相关，必须一并修复

## Decision

采用 **方案 (a)：进程内定时快照 + 文件轮转**，并同步将 `persistDb` 改为原子写。零新增依赖。

备份机制规格：
1. `DataStore` 新增 `backup(backupDir)` 方法：取内存库 `db.export()`，经 tmp 文件 + `fs.renameSync` 原子写入 `data/backups/backup-YYYYMMDD-HHmmss.db`
2. 独立模块 `backup.js` 提供调度器：`setInterval` 默认每 6 小时触发一次，定时器调用 `.unref()`，不阻塞进程退出，也不在测试/jest 环境运行
3. 轮转策略：按文件名时间戳排序，仅保留最新 `BACKUP_KEEP`（默认 7）份，更早的删除
4. 备份目录 `data/backups/` 位于数据卷内，随现有 `./data:/app/data` 挂载持久化，无需改 compose 卷配置
5. `persistDb` 原子化：先写 `data.db.tmp` 再 `rename` 到 `data.db`——同一文件系统上 rename 是 POSIX 原子操作，彻底消除写盘中途崩溃留下半个库的窗口
6. 优雅停机（SIGTERM/SIGINT）时停止调度器，避免容器重启风暴期间的重复备份

## 候选方案对比

| 维度 | (a) 进程内 setInterval 快照 | (b) 系统 cron + shell 脚本 | (c) 每次写操作时快照 |
|---|---|---|---|
| 部署侵入 | 无：逻辑在应用进程内，三种 compose 形态开箱即用 | 高：需宿主机 crontab 或额外 sidecar 容器，与"单容器一键部署"的现有形态冲突；CI/CD 自动部署后还需额外配置宿主机 | 无 |
| 快照一致性 | 好：`db.export()` 从内存库直接导出，逻辑一致 | 差：shell `cp data.db` 是对磁盘文件做文件级拷贝，若恰好撞上 `persistDb` 写盘会拷到半个文件 | 好 |
| 资源开销 | 每 6 小时一次全量导出（库为 KB 级，开销可忽略） | 同左 | 每次保存都写两份全量；配合限流上限 50 次/15min，最坏情况磁盘写放大 50 倍，且多数快照内容相同，无信息增量 |
| 备份粒度 | 时间维度，可预测，保留策略简单 | 同左 | 版本维度，能救回"误保存"，但文件数量与写频线性相关，轮转窗口极短（保留 7 份 = 最近 7 次保存） |

结论：方案 (a)。方案 (b) 与容器化部署形态冲突且有一致性缺陷；方案 (c) 的写放大在"防刷库"目标下反而成为攻击面。误保存回滚需求由 6 小时粒度 + 7 份保留（约覆盖 42 小时历史）折中满足。

## Consequences

**正面**：
- 备份与主库共用同一原子写路径，磁盘上任何时刻都是完整可用的 SQLite 文件
- 零新增依赖、零部署改动，宿主机上 `ls data/backups/` 即可核验
- `persistDb` 原子化同时惠及主数据文件，是本轮加固中"防数据丢失"收益最大的一项

**负面**：
- 备份在应用进程内，若宿主机磁盘整体故障，备份与主库同归于尽（升级路径：未来可加 rclone/scp 推送到异地，超出本轮范围）
- 备份为全量复制，若库增长到 MB 级以上需重估间隔（当前导航数据 KB 级，不构成问题）
- 进程不运行时不产生备份（Docker `restart: unless-stopped` 保证常驻，可接受）
