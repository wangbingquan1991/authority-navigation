# ADR-004: 整库替换语义下增加「空写保护」，并以写前快照作兜底

## Status: Accepted (2026-09-16)

## Background

线上出现「更新部署后自定义数据全部消失」的故障。排查结论是存储与缓存本身未损坏，`data.db` 被覆盖成了空库，而 `backups/*.db` 中的历史数据完好。根因是三个设计缺陷叠加：

1. **服务端是整库替换**：`DataStore.write()` 先 `DELETE FROM custom_links` / `DELETE FROM custom_categories`，再插入客户端提交的数据。没有 merge、没有 diff。
2. **服务端对空载荷照单全收**：`validatePayload()` 对缺失字段填默认值，因此 `POST {}` 会被校验通过并视为合法数据，等价于「清空全库」。
3. **前端每次回写整个内存状态**：`saveAllData()` 在 API 模式下把内存中的全量数据 POST 出去。只要某一刻内存状态为空（加载失败、读到空、旧版 / 缓存前端、登录前回写），就会发出空写。

三者叠加的结果是：**任何一个瞬间的空状态都能秒删全库**。触发链推测为部署后浏览器仍加载旧版前端，对着新版后端发出结构不兼容或空状态的写入。

此外还发现一个放大问题的缺陷：`detectApiMode()` 把探测失败（含未登录时的非 200、网络抖动）**永久缓存为 `false`**，导致前端此后一直停留在 localStorage 空模式，既读不到也写不进服务端数据。

## Decision

采用「默认拒绝 + 显式放行 + 写前留档」三层防护，不改变 `write()` 的整库替换语义。

**1. 服务端空写守卫（权威防线）**

`POST /api/data` 在鉴权与载荷校验之后增加判断：若**库中已有数据**而本次提交的载荷为空，直接返回：

```
409 { "error": "Refused to overwrite existing data with an empty payload", "code": "EMPTY_OVERWRITE" }
```

并**不写入**，既有数据原样保留。判定「为空」的口径是全部内容字段都为空：`customLinks` 无分组、`customCategories` / `removedDefaults` / `removedCommonLinks` / `categoryOrder` 均为空数组。

**2. `allowEmpty` 显式放行**

确有清空意图的调用方（前端「恢复默认」、全量还原备份）需在请求体中携带 `allowEmpty: true`，否则同样被拒。库本身为空时提交空数据是合法空操作，直接放行。

**3. 前端源头防护**

- `saveAllData()` 对空数据默认不发送：数据可信时弹确认框，用户确认后才以 `allowEmpty` 重试；数据不可信时直接拒绝并提示刷新。
- **从未成功读到服务端数据时禁止整库覆盖**。这是比「空写」更隐蔽的一类风险：内存里若只有一份「基于空壳」的残缺快照，写出去的载荷非空但与服务端真实状态不符，同样会造成部分数据丢失。用 `remoteDataLoaded` 标记「是否成功读到过服务端数据」作为闸门。
- `loadAllData()` 返回深拷贝，避免各 `save*` 封装的「读-改-写」直接把缓存改脏——写入失败时内存与磁盘会不一致。

**4. 修复 `detectApiMode()` 的永久缓存缺陷**

只缓存**确定结论**：`true`（确认有后端，含 401/403/429 这类「服务端在但拒绝本次读取」）与 `false`（确认为纯静态部署，如 404）。5xx 与网络异常属临时故障，**不缓存**，下次调用重试，避免一次抖动把前端永久降级到本地模式。

**5. 写前快照（运维兜底）**

`write()` 在 `DELETE` 之前把当前库导出为 `data/backups/pre-write/pre-write-YYYYMMDD-HHmmss-SSS.db`，仅保留最新 10 份，独立于定时备份轮转。仅当库中确有用户内容（链接、分类，或非空的移除 / 排序记录）时才留档，避免空写空产生无回滚价值的文件。快照失败只记日志、不阻断写入（它是兜底，不是闸门）。

## 候选方案对比

| 维度 | 本方案（守卫 + allowEmpty + 快照） | 改成 merge / upsert 式写入 | 前端单点防护 |
|---|---|---|---|
| 挡住空写清库 | 是（服务端权威拦截，旧前端也挡得住） | 是 | 否：旧版 / 缓存前端绕过前端逻辑 |
| 改动面 | 小：一个守卫 + 一个选项 + 快照函数 | 大：需重新定义删除语义、冲突合并策略 | 最小 |
| 数据模型影响 | 无 | 需引入 `replace: true` 区分全量/增量，前端所有写路径要复查 | 无 |
| 可回滚性 | 高：秒级写前快照 | 高 | 无 |
| 风险 | 低 | 高（删除语义设计错误会造成更难察觉的数据残缺） | 高（防线在客户端，不可信） |

结论：整库替换语义本身不是缺陷，真正的缺陷是「空载荷被当成合法数据」。因此选择**默认拒绝空写 + 显式放行**，把 merge 式改造（原方案④）推迟——它需要先设计好删除语义，风险高于本次故障的收益。

## Consequences

**正面**：

- 任何来源的空写（旧前端、缓存前端、异常加载）都无法再清空全库，防线在服务端，客户端不可绕过
- 写前快照把可回滚粒度从 6 小时提升到单次写入
- `detectApiMode()` 不再把临时故障固化为永久降级，「数据看起来消失」的另一条路径被堵住
- 未读到服务端数据时的整库覆盖被禁止，堵住「非空的残缺载荷覆盖」这一更隐蔽的路径

**负面**：

- 删除最后一个自定义分类 / 链接时会多一次确认弹窗（数据可信时）
- `allowEmpty` 是「信任调用方声明」的设计：持有有效登录态的攻击者仍可主动清空，这是单管理员场景下可接受的边界（该操作本就在其权限内）
- 写前快照增加一次 `db.export()` 开销；数据量为导航链接级别（KB 量级），影响可忽略
