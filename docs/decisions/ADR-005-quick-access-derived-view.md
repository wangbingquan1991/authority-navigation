# ADR-005: 快捷入口改为「全站链接的派生视图」，排序完全由使用行为驱动

## Status: Accepted (2026-09-17)

## Background

「快捷入口」在数据层沿用历史键名 `常用链接`。改造之前，它是**一个被当成分类渲染的固定清单**：

1. **候选池是硬编码的两段拼接**：默认精选 `config.commonLinks` 加 `customLinks["常用链接"]`。这意味着用户在任何**其他**分类里自建的网址，无论点击多少次都不可能出现在快捷入口里——它压根不在候选池中。用户反馈「自定义添加的网址不在点击频率统计中吗？」，根因就在这里。
2. **归类错误**：它以分类卡片的外壳渲染（有背景面、边框、图标、计数徽标），与下方分类卡片同构，被读作「又一个分类」，而它实际承担的是高频快捷栏的角色。
3. **排序与语义耦合**：点击频率被当作一个可选的排序手段塞在分类渲染里，而不是这个视图的存在理由。

## Decision

**1. 快捷入口是派生视图（derived view），不是分类、不是容器**

它不拥有链接。内容全部来自其他分类，视图只决定「展示哪些、按什么顺序」。因此界面渲染为一条**无卡片外壳的横向胶囊条**（透明背景、无边框、无圆角、无分类图标、无分类级标题），与分类卡片在视觉上解耦；显示名「快捷入口」与持久化键「常用链接」**刻意分开**，键名不可改动，否则既有用户数据全部失联。

**2. 候选池 = 全站可见链接**

`buildQuickAccessPool()` 收集：各默认分类的链接（含用户在其中自建的）+ 自建分类的链接 + 用户显式加入快捷入口的链接，按 URL 去重、剔除已移出记录（`removedCommonLinks`）。因此**任何网址只要用得多就会自动浮上来**，无需人工维护清单。

**3. 排序完全由使用行为驱动**

`rankQuickAccess()` 的排序键依次是：`hourlyFreq` 降序 → `lastClick` 降序 → 冷启动顺序。冷启动（尚无任何点击记录）才回落到分段顺序：用户显式加入的 > 默认精选 > 其余链接，各自保持原始顺序。展示上限 `QUICK_ACCESS_LIMIT = 25`。

池构建与排序都抽成**零依赖纯函数**（`pages/js/utils/quickAccess.js`），因此可以在 `vm` 里直接加载真实源码做单测，不必维护逻辑副本。

**4. 三种手势，三种语义**

| 手势 | 含义 | 数据动作 |
|---|---|---|
| 从分类拖入横条 | 固定（pin） | `addCustomLink("常用链接", …)`；**不**把链接从原分类移走 |
| 从横条拖到某分类 | 改分类 + 解除固定 | 加入目标分类；解除固定；**不**写 `removedCommonLinks`，因此它仍可凭使用频率回到横条 |
| 点胶囊上的 × | 移出 | `removeCustomLink` + **一律**写 `removedCommonLinks` |

× 必须一律写移出记录：候选池现在是全站的，只删自建记录的话，该链接会立刻从它所属的分类重新进入候选池，「移出」等于没做。

**5. 概念分离：`custom` 与 `sourceIsStock` 不可混用**

- `custom` = **用户自建**的链接（相对配置里的原有条目）。
- `sourceIsStock` = 它是**默认分类里的原有条目**，决定把它移出该分类时要不要写 `removedDefaults`（自建链接删掉自建记录即可，原有条目必须拉黑，否则立刻回到原分类）。

改造中曾出现一个真实缺陷：候选池把「被固定到快捷入口」这件事错当成了「用户自建」，导致一条原有条目从横条拖出后不再被记入 `removedDefaults`，于是它既留在原分类、又出现在目标分类。现在「固定」只影响排序优先级，**不再影响任何身份判定**；`sourceIsStock` 在池里生成一次，随拖拽载荷传递。拖拽载荷有两种来源（分类卡片发 `isCustom`，横条胶囊发 `sourceIsStock`），`app.js` 在入口处用 `link.sourceIsStock ?? (link.isCustom !== true)` 统一成同一种判断。

**6. 导出仍导出「配置来源」，不导出排序结果**

`getQuickAccessSources()` 返回的是可复现的输入（默认精选去掉已移出的，加上显式加入的），而不是随点击变化的排序快照——备份/迁移需要的是输入，不是某一刻的视图。

## 候选方案对比

| 维度 | 本方案（全站池 + 派生视图） | 继续硬编码清单，仅修统计口径 | 把高频链接写成真实分类并动态搬移 |
|---|---|---|---|
| 自定义网址能否凭频率进入 | 能，任何分类里的都算 | 不能，池子里没有 | 能 |
| 数据一致性 | 高：横条不持有数据，无同步问题 | 高 | 低：需要持续搬移链接，分类归属被频率劫持，用户手改分类会被覆盖 |
| 用户可控性 | 高：拖入=固定、×=移出 | 高 | 低：无法表达「它本来就属于这个分类」 |
| 改动面 | 中：新增纯函数模块 + 三处手势语义 | 小 | 大：写操作定时触发、冲突策略复杂 |
| 可测性 | 高：纯函数，单测覆盖池与排序 | 中 | 低 |

结论：横条是**观察窗口**而不是**存储容器**，所以链接归属不变、只有展示顺序变——这既满足了「完全由使用行为驱动」，又不与用户手动的分类管理冲突。

## Consequences

**正面**：

- 任何网址（含自建分类里的、其他分类里自建的）都能凭使用频率自动浮到前面，不再需要人工维护清单
- 横条与分类卡片视觉解耦，不再被读成「一个分类」
- 池构建与排序是纯函数，22 项单测直接跑真实源码
- 三种手势语义互不干扰：固定只影响顺序，移出才影响可见性

**负面 / 已接受的取舍**：

- **冷启动只能靠默认精选**：没有任何点击记录时，横条展示的就是 `config.commonLinks` 前 25 条
- **移出以 URL 为键**：同一 URL 出现在多个分类时会被一并抑制（与 `removedDefaults` 的既有口径一致）
- **点击统计存在浏览器 `localStorage`**：换设备或清缓存后排序回落到冷启动顺序
- **`getHourlyFrequency` 是「热度」而非严格平滑频率**：它按「首次点击至今的小时数（下限 0.1 小时）」折算，因此新链接在前几分钟会被放大（约 10 倍）。这是刻意的：让刚刚开始使用的链接能立刻浮上来，代价是它不等价于长期平均点击率
